## 1. 问题根源（已证实）

NVIDIA App/GFE（Alt+F1）与 Xbox Game Bar / Win11 截图工具在 HDR 显示器下的截图，是把 Windows DWM 合成器的原始像素直接封装进 JPEG XR（.jxr）：

| 项目 | 规格 | 置信度 |
|---|---|---|
| 像素语义 | **scRGB 线性浮点**：BT.709 原色、γ=1.0、**1.0 = 80 nits**（SDR 参考白） | Verified |
| 位深两档 | **NVIDIA 覆盖层 = FP32**（`GUID_WICPixelFormat128bppRGBAFloat`）；**Win11 截图工具 / Game Bar = FP16**（`64bppRGBAHalf`） | Verified |
| 数值范围 | 远超 [0,1]：>1.0 是 HDR 高亮；**负值合法**（出 sRGB 色域的补色）；JXR 定点编码范围 −4..+4 | Verified |
| 元数据 | 标准 JXR 容器（Exif/XMP），一般**无 ICC**，WIC 按浮点格式直接推断 scRGB | Verified |
| 官方出路 | **NVIDIA App 无格式选项**：SDR 存 PNG、HDR 强制 JXR；Win11 截图工具 HDR 下同样强制 .jxr | Verified/Supported |

**为什么市面工具全失真（三层断裂，源码级核实）**：
1. **解码层**：JXR 唯一开源实现 jxrlib 自 CodePlex 关停后零维护；FFmpeg/**libvips/Pillow/OpenCV 完全没有 JXR 解码器**；能解的只有 Windows 私有 WIC，而 WIC 默认 FormatConverter 一律转 8bppBGRA——多数工具在"取像素"一步就把 HDR 削成 8bit SDR。
2. **数据层**：载荷是 scRGB 线性浮点而非 PQ，按普通图读 → >1.0 全被 clamp 成过曝白块（MS Q&A 600+ 人同问）。
3. **编码层**：保真输出需要 scRGB→PQ 变换 + cICP/NCLX 标签，这些零件 2023–2024 才就位（PNG cICP、AVIF muxer、avifenc `--cicp`、浏览器 HDR 支持）且分散在各库中，**没有任何现成管线把它接到 JXR 解码上**。

## 2. 现有方案盘点

| 工具 | 保 HDR？ | 说明 |
|---|---|---|
| **ledoge/jxr_to_png**（70★，2026-08 仍维护） | ✅ **唯一成熟成品** | C++ + WIC 浮点解码 + libpng；输出 16bit PNG、BT.2100 PQ（数据量化 10bit）、MaxCLL 取 99.99 百分位（规避 Chromium 整体调暗）；CLI + 拖拽；仅输出 PNG 一种格式 |
| jxrlib / JxrDecApp | ✅（懂行可用） | `-o tif -c 15/25` 可出浮点 TIFF，但停在 2009 时代代码 |
| justlovediaodiao/jxr2uhdr（4★） | ✅（先行者） | Avalonia 桌面应用，JXR→UltraHDR JPEG；**README 失实（照抄 jxr_to_png）**，采用度极低，质量未经验证 |
| ImageMagick | ❌ | 无原生 coder，靠外部委托 JxrDecApp→TIFF；scRGB 语义丢失、png.c 无 cICP |
| FFmpeg | ❌ | **完全没有 JXR 解码器**（官网格式表核实）；仅当编码出口可用 |
| hdrfix（173★）、NVIDIA-HDR-Converter-GUI、AutoHDRConvert | ❌（故意 SDR） | 方向相反：tonemap 成 SDR |
| 照片 App / 画图 / 在线转换站 / XnView / Lightroom | ❌ | 8bit SDR 导出或根本不支持 |

**空白点 = 本工具的定位**：一站式 **JXR → {UltraHDR JPEG、HDR AVIF、HDR PNG}** 批量转换 + Windows 原生易用性（右键/拖拽），补上"分享格式选择"与"零门槛打包"两块。

## 3. 分发格式怎么选（2025–2026 兼容性矩阵精简版）

| 格式 | Chrome/Edge | Safari | Win11 原生 | Android 相册 | 微信 |
|---|---|---|---|---|---|
| **UltraHDR JPEG**（gain map） | ✅（Chrome 116 旗标→后默认） | ✅ Safari 26 | SDR（需 BandiView 等） | ✅ 14+ 默认 | iOS「查看原图」✅；普通图片一律 SDR |
| **HDR AVIF**（10bit PQ） | ✅ Chrome 85+ | ✅ Safari 26 | SDR | SDR | SDR；发"文件"保留 |
| **HDR PNG**（cICP） | ✅ Chrome 117+ | ✅ Safari 26 (Likely) | ❌ | SDR | SDR；发"文件"保留 |
| JPEG XL | Chrome 155+ 回归 / Edge 未跟 | 部分 | ❌ | ❌ | ❌ |
| 保留 JXR | ❌ | ❌ | ✅ **原生唯一真 HDR** | ❌ | ❌ |

**优先级结论**：
1. **UltraHDR JPEG = 默认分享格式**（SDR 万能兜底 + 主流浏览器真 HDR + Android 14+ 原生）
2. **HDR AVIF = 网页/技术受众**（体积小、Chrome 支持最久）
3. **HDR PNG = 无损存档**（未来浏览器生态）
4. 微信铁律：勾"原图" + 对方点"查看原图"才见 HDR（iOS↔iOS 可靠；iOS→安卓常丢）；IM 走"文件"传输保留 HDR 字节。

## 4. 设计方案

### 4.1 产品定位与形态（回答"工具还是打包成什么"）

**做一个 Windows 桌面小工具，三层形态递进：**

| 阶段 | 形态 | 说明 |
|---|---|---|
| M1 | **单文件 CLI `hdrshot.exe`**（NativeAOT，~5MB，零依赖） | `hdrshot a.jxr` / `hdrshot *.jxr -o out/`；**支持把 .jxr 拖到 exe 图标上**（取 argv 即可） |
| M2 | **资源管理器集成** | 右键菜单"转换为 HDR JPEG/AVIF"（.reg 脚本注册 `HKCR\SystemFileAssociations\.jxr\shell\...`）+ `SendTo`；便携 zip，无需安装器 |
| M3（可选） | 轻量 GUI（WinForms/WPF） | 拖入批量、输出格式勾选、SDR 白电平滑条同步、预览对比 |

**打包方式**：GitHub Releases 便携 zip（`hdrshot.exe` + 1–2 个小编码组件 dll/exe）；可选 winget manifest。**不上 Microsoft Store**（审核与依赖麻烦，便携分发足够）。M1 用 NativeAOT 单文件是为了"双击即用、无 .NET 运行时要求"。

### 4.2 技术架构（推荐管线，保真优先）

```
.jxr ──WIC 解码──> float[] scRGB ──转换──> PQ BT.2020 10bit ──编码──> 输出
        (128bppRGBAFloat)      (×80nits→矩阵→ST2084)      ├─ UltraHDR JPEG (M2, libultrahdr)
        GetPixelFormat 区分                               ├─ HDR AVIF    (M1, libavif/avifenc)
        NVIDIA=FP32 / 系统=FP16                            └─ HDR PNG+cICP (M1, 手写 chunk)
                              └─(可选支路) SDR tonemap → sRGB JPEG 兜底
```

**解码端（Verified 可行）**：C#/.NET 8 通过 COM interop 调 WIC（`IWICImagingFactory`）：
- `GetPixelFormat()` 识别 `64bppRGBAHalf` / `128bppRGBAFloat`（顺带提示来源是系统截图还是 NVIDIA）；
- `IWICFormatConverter` 统一转 `128bppRGBAFloat`（CanConvert 需实测，风险点 R1）；
- 取 `IWICColorContext` 透传 Exif/XMP。
- 参考实现：`ledoge/jxr_to_png`（C++ 同路径）、`jxr_to_png` 的 WIC 用法可 1:1 移植到 C#。

**转换端（公式 Verified）**：
- 线性亮度：`nits = scRGB × 80`；负值 clip 至 0（libplacebo/KWin 同做法，scRGB 正值必落在 BT.2020 内，无需 gamut mapping 库）；
- `BT.709 → BT.2020` 3×3 矩阵 → `Y/10000` → **ST 2084 PQ**（c1=0.8359375, c2=18.8515625, c3=18.6875, m=78.84375, n=0.1593017578125）；
- MaxCLL 取 99.99 百分位（jxr_to_png 同法，规避 Chromium 按 H.274 全图调暗）；
- SDR 支路（输出兜底 JPEG 用）：PQ→显示亮度 → BT.2408 1000-nit 参考白或 Hable tonemap → 精确 sRGB 分段 OETF → 8bit；**SDR 白电平做成设置项**（DWM 滑条通常 4×80nits+）。

**编码端**：
| 输出 | 组件 | 输入要求 | 工作量 |
|---|---|---|---|
| HDR AVIF | libavif.dll P/Invoke（`avifImage` CICP=(9,16,9) 即 nclx）或捆绑 avifenc.exe | 10bit YUV420 PQ | 小 |
| HDR PNG | System.Buffers 自写 16bit PNG + **手写 cICP chunk**（4 字节 (9,16,9,1)+CRC32 插在 IDAT 前，Verified 极易） | 10bit PQ RGB16 | 小 |
| UltraHDR JPEG | libultrahdr（MSYS2 有 mingw-w64 包，可 CMake 自编；P/Invoke 或捆绑 ultrahdr_app.exe） | P010(PQ) + NV12(SDR) raw，gain map 库内自动算 | 中 |
| SDR JPEG 兜底 | SkiaSharp / libjpeg-turbo | tonemap 后 8bit | 小 |

### 4.3 备选路线（对比后不推荐但保留）

- **B：扩展 jxr_to_png（C++）**：它已解决解码+PQ+cICP，加 libavif/libultrahdr 出口即可；优点是最少新轮子、可直接给上游提 PR；缺点是 C++ 维护与 GUI 化更重。若 M1 顺利可考虑双轨。
- **C：Python 原型**（pythonnet 调 WIC + `hdr-conversion` 库 + imagecodecs）：最快验证数学正确性，但 PyInstaller 打包臃肿、不适合最终分发。仅作 M1 前的数值验证沙盘。

### 4.4 验证方案（Acceptance）

1. **测试语料**：微软官方 HDR 样本 `https://aka.ms/hdr-backgrounds-wip` + 你自己的 NVIDIA FP32 截图 + 截图工具 FP16 截图（覆盖两档位深）。
2. **数值保真**：解码 scRGB float 直方图 vs 输出文件逆变换回 scRGB 的对比——高光区（>80nits）逐级保留、无 clamp 白块；PQ 往返误差 < 10bit 量化步长。
3. **元数据**：`avifdec --dump` / PNG chunk 查看器确认 CICP=(9,16,9)、cICP 存在、MaxCLL 合理。
4. **目检矩阵**：本机 Chrome/Edge（HDR 屏）显示真 HDR；Android 手机相册看 UltraHDR；微信 iOS「原图+查看原图」链路实测。
5. **回归**：SDR 支路输出与 hdrfix 目视对比（HDR→SDR 质量基准）。

### 4.5 风险与开放问题

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | WIC FormatConverter 到 float 格式的 CanConvert 路径需实测 | 低 | 不转换直接 `CopyPixels` 原生格式（half/float 两分支各自处理）；jxr_to_png 已证明可行 |
| R2 | libultrahdr Windows 构建长期维护 | 中 | M1 先交 AVIF+PNG；UltraHDR 可先捆绑 MSYS2 预编译 dll，必要时锁版本 |
| R3 | 微信 iOS→安卓 HDR 丢失、Windows 原生看不了 UltraHDR | 生态限制，工具无法解决 | 文档写明使用姿势；可选同时输出 JXR 拷贝给 Windows 用户 |
| R4 | SDRWhiteLevel 滑条影响 SDR 支路观感 | 低 | 做成 GUI 设置项 + 默认 BT.2408 |

## 7. M1 实施与验证记录（2026-09）

**已落地**：`src/hdrshot`（C# .NET 8，WIC COM 互操作解码 + 纯 .NET PNG 编码 + avifenc 外部编码），构建通过，5 个微软官方样本全部转换成功；`dist\` 为自包含便携发行目录（hdrshot.exe + tools\avifenc.exe 及依赖 DLL）。

**验证结果（全部实测）**：
- 5 个微软官方 HDR 样本（3840×2560，`64bppRGBAHalf` FP16 scRGB）全部转换成功；
- 与参考实现 ledoge/jxr_to_png 逐像素比对（自研 WIC 回读比对通道 `hdrshot comparepng`）：**99.96% 像素完全一致**，差异样本全部恰为 64/65535 = 1 个 10-bit 量化步长（SSE 浮点 vs double 阈值表的舍入差）；
- MaxCLL/MaxFALL 与参考实现**逐位一致**（898/143、1284/247、1189/174、1238/198、1406/233）；
- PNG 字节级核验：`cICP = 09 10 00 01`（BT.2020/PQ/RGB 恒等/全范围）、`cLLi` = 898.16/142.95 nits，位置合规（IHDR 后、IDAT 前），WIC 可直接回读；
- AVIF 端到端：avifenc 1.4.2（aom 3.15.1/dav1d 1.5.4/rav1e/svt-av1）→ **10-bit PQ BT.2020，CICP (9,16,9) 精确写入**，YUV444，0.4 MiB（约为 PNG 的 1/28），dav1d 解码回读校验通过。

**实施中的新发现（对 §1 生态分析的补充）**：
1. **Windows 11 25H2（Build 26200）已不再注册 WIC1 工厂 CLSID `{CACAF262…}`（REGDB_E_CLASSNOTREG）**，只有 WIC2 `{317D06E8…}` 可用——硬编码 WIC1 的老工具在新系统直接失效，属于"市面工具坏了一圈"的又一根因。hdrshot 已切 WIC2 + 双 IID 运行时回退。
2. COM 派生接口 vtable 顺序 = **基类方法在前**（IWICFormatConverter 的 GetSize…CopyPixels 先于 Initialize）；IWICBitmapDecoder 在 GetFrame 前有 9 个方法；CreatePalette 卡在 CreateFormatConverter 前面——互操作定义必须逐条对照官方 wincodec.idl（tpn/winsdk-10），不可凭记忆或 mingw 片段。网上流传的 "IWICImagingFactory IID = 35d1c17ad0cd" 并不存在于官方 IDL（真值 54d7a935ff70）。
